## Question

The target is not minimum source lines and not a port of HRA's domain model.

The stronger hypothesis remains:

> Can LOAM recover a broad daily-use household interface from a small set of independently meaningful parts, explicit relations, query coordinates, projections, and local laws?

The pressure is on **semantic multiplication**. A new household capability should not automatically earn a new Core noun, state machine, stored aggregate, or top-level UI ontology.

## Current production checkpoint

Since the original prototype-era matrix:

- the numbered TUI prototype chain is no longer the implementation path;
- one production `loamTui` exists;
- Home / Actual / Scheduled production interaction is established;
- Record uses shared Movement admission and publication, including stale-preview rejection;
- shared `ActualReview` and `ScheduledReview` boundaries exist;

- Observation 218 extracted finite partial-injective replacement-frontier mechanics across Event Correction, ActualValidity, Scheduled Replacement, and QuantityBasis while preserving their separate semantic families and reducing production-shaped Application implementation by a net 90 lines.

The practical conclusion is now:

> basic daily-use TUI recovery no longer needs to wait for a broad architecture cleanup.

The larger gap to HRA is primarily delivery maturity and interaction density.

## Composition ladder

Before adding retained meaning for a requested capability, pressure-test in order:

```text
0. presentation only
1. projection
2. explicit relation
3. query coordinate / policy
4. new retained semantic part
```

Failure at one rung is evidence, not permission to jump immediately to rung 4.

## Still semantically sharp

- Backing;
- some accounting and report classification questions.

## Lane A: daily-use UI recovery — PRIORITY NOW

Recover useful HRA affordances over current LOAM semantics without porting HRA's domain model.

Recommended order:

```text
1. Home / navigation usability
   - direct entry to existing workspaces
   - consistent help / back / focus preservation

2. Actual workspace usability
   - browse / detail
   - reuse the one Record editor
   - correction / reverse flow through existing boundaries
   - scrolling only when real lists require it

3. Scheduled workspace
   - create
   - complete as Actual
   - cancel
   - replace
   - no recurrence or completeness invention

4. Attention workspace
   - browse / detail first
   - then qualified close / realize / continue actions

5. Capacity workspace
   - movement editor
   - before / after preview

6. Reports
   - start with semantically ready projections
   - expand only when query semantics are qualified

7. shared UI mechanics
   - extract scrolling, mouse input, forms, etc. only after multiple real LOAM surfaces need the same law
```

The UI is deliberately a pressure instrument. When a useful interaction cannot be built without inventing meaning locally, return to focused semantic observation.

## Lane B: semantic / mathematical simplification — DEFERRED, OBSERVE

Observation 218 established the desired success pattern:

```text
repeated production mechanics
  -> identify a small mathematical structure
  -> prove the factorization
  -> preserve domain meanings locally
  -> extract only when production implementation actually gets smaller or safer
```

Do **not** keep abstracting merely because code shapes resemble each other while daily-use capability remains behind HRA.

### Deferred candidates

Keep these visible, but do not treat them as blockers:

- finite partial-map / lookup / permutation mechanics across memory families;
- persistence-topology fanout and repeated codec / authority wiring;
- further Application mechanics extraction;
- information-order / lattice structures for evidence absence versus known values.

### Revisit trigger

Resume this lane when at least one is true:

- a new practical feature would duplicate the same structural mechanism again;
- changing one structural law requires synchronized edits in three or more semantic families;
- TUI work exposes actual semantic leakage or a second local engine;
- a proposed shared structure can be proved small and produces a concrete reduction or safety gain comparable to Observation 218.

Until then, UI pressure wins priority.

## HRA comparison discipline

Use HRA as:

- operational continuity;
- a catalog of useful affordances;
- a source of concrete household pressure;
- a comparator for interaction quality.

Do not import automatically:

- HRA package boundaries;
- Account / Plan / Envelope / Cycle / Series vocabulary;
- report object structure;
- persistence shape;
- HRA UI state machines.

For every HRA affordance ask:

```text
Can existing LOAM evidence + projection + presentation recover the useful answer or action?
```

Only counterexamples should earn new retained meaning.

## Measurement

For every restored capability, record:

```text
Core families added            N
canonical relation kinds added N
query coordinates/policies     N
new projections                N
existing laws reused           N
new local laws                 N
presentation-only mechanisms   N
```

LOC is not the primary success metric.

Observation 218 is evidence for a stronger rule: a mathematical abstraction earns production status only when the repeated structure is real, semantic families remain distinct, and the resulting implementation is concretely smaller or safer.

## Refutation criteria

Weaken the hypothesis rather than protecting it if practical recovery repeatedly requires:

- new Core families merely to distinguish ordinary UI actions;
- relations so generic that illegal combinations proliferate;
- projections that require hidden policy;
- a small vocabulary that makes safe writers harder than explicit evidence would;
- a shared UI abstraction whose state space is larger or less provable than several local state machines;
- real household questions that require retaining a distinction previously assumed derivable.

A counterexample is a useful result.

## Immediate next gate

Do **not** perform another general architecture-cleanup pass first.

Start from current production main and inspect the **Home / Actual HRA usability gap**. Choose the smallest high-frequency affordance that is already semantically qualified, implement it through existing shared boundaries, and use the resulting dogfood pressure to decide what needs semantic work next.

Any newly exposed semantic hole returns to Lane B for a focused observation rather than being patched locally in TUI.
